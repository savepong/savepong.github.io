คืองี้ครับ มีเคสนึงที่ผมอยากเล่าให้ฟัง เพราะมันเป็นกับดักที่คนใช้ Supabase โดนกันได้ง่ายมาก

อาการคือแอปมัน "โหลดไม่ขึ้น" เป็นช่วง ๆ ทั้งวัน แต่หนักสุดตอนเช้า ฟังแค่นี้ทุกคนก็เดาเหมือนกันหมดแหละ — เครื่องเล็กไป ตารางใหญ่ไป query หนักไป

แล้วรู้ไหมครับว่าตอนไล่ดู มันเจอครบทั้งสามข้อจริง ๆ

DB ตัวโปรดักชันรันอยู่บนสเปคเล็กสุด แถมแชร์กับอีกแอปนึง มีตาราง feed ชั่วคราวที่โตไปถึงล้านกว่าแถว เกือบหนึ่งกิกะไบต์ แล้วก็มี query ที่ไป aggregate ข้อมูลทั้งก้อนก่อนค่อย LIMIT

แก้ไปหมดทุกข้อครับ

**แล้วอาการก็ยังอยู่** เพราะไม่มีข้อไหนเลยที่เป็นต้นเหตุจริง

## กับดักของ "ดูเหมือนคืบหน้า"

อันนี้แหละที่ผมว่าน่าสนใจที่สุดในเคสนี้ ปัญหาปลอมสามอย่างที่ "จริง" ทุกอย่าง มันอันตรายกว่าไม่เจออะไรเลยอีก เพราะคุณจะรู้สึกว่ากำลังเดินหน้า กราฟสวยขึ้นนิดนึง แล้วก็หลงทางต่อไปอีกสัปดาห์

สิ่งที่ชี้ทางจริง ๆ คือ **เวลา** ครับ ทำไมต้องเป็นช่วงเช้า ๆ

เพราะช่วงเช้าคือเวลาที่พนักงานนั่งกดอนุมัติรายการค้างกันรัว ๆ ไง นั่นไม่ใช่ปัญหาเชิงเทคนิค นั่นคือพฤติกรรมของคนใช้งาน

## ต้นเหตุจริง

ทุกครั้งที่กดอนุมัติหนึ่งรายการ โค้ดจะเรียก use case ที่ไป "รีเฟรชสถานะ" ของสัญญาที่ยังมีชีวิตอยู่ **ทุกแถว** ประมาณสามพันกว่าแถว — เขียนทับหมด แม้ค่าเดิมกับค่าใหม่จะเท่ากันเป๊ะ

แล้วตารางนั้นดันมี Database Webhook แบบ row-level ติดอยู่ ชนิด `AFTER UPDATE ... FOR EACH ROW` **โดยไม่มี `WHEN`**

ผลคือ กดหนึ่งที ยิง HTTP POST กลับเข้า API ตัวเองสามพันสี่ร้อยกว่าครั้ง ภายในไม่กี่วินาที

ตัวเลขจริงที่วัดได้: **374,200 ครั้งใน 5 วัน** พีคที่ 3,400–4,584 ครั้งต่อนาที ในช่วง 09:15–10:30 ของทุกวัน ตารางนั้นมีแค่ 3,856 แถว แต่โดน update ไป 593,226 ครั้ง

ส่วน handler ปลายทางน่ะเหรอครับ มันสนใจแค่เคสเดียว — สถานะเปลี่ยนเป็นปิด และเป็นการส่งแบบพัสดุ ที่เหลืออีกสามพันกว่าสายคือโยนทิ้งหมด

เทียบง่าย ๆ เหมือนออดไฟไหม้ทั้งตึกที่ดังทุกครั้งที่มีคนเปิดประตูห้องไหนก็ได้ แล้วค่อยให้ รปภ. วิ่งไปเช็กทีละห้องว่าห้องไหนไฟไหม้จริง ออดไม่ได้พัง แต่มันถามผิดคำถามตั้งแต่แรก

และตัว API ก็จมไปพร้อม connection pool ที่มีแค่ 10 เส้น

## แก้ยังไง

สามชั้นครับ

ชั้นแรก สร้าง trigger ใหม่โดยใส่ `WHEN` ให้ตรงกับเงื่อนไขที่ handler สนใจจริง ๆ — ให้ตัวกรองอยู่ที่ฝั่ง DB ไม่ใช่ปล่อยมาแล้วค่อย return ทิ้ง

ชั้นสอง แก้โค้ดให้เขียนเฉพาะแถวที่สถานะ "เปลี่ยนจริง" งานรีเฟรชที่บอกว่า idempotent ถ้ามันยังเขียนทับแถวที่ไม่เปลี่ยน มันไม่ idempotent ครับ มันยังจุด trigger ยังเขียน WAL ยังทำให้ตารางบวม

ชั้นสาม ตั้ง `statement_timeout` ที่ฝั่ง client พร้อม connect/idle timeout แล้ว map timeout ให้กลายเป็น 503 ที่ retry ได้ ไม่ใช่ 500 ที่ตายเฉย ๆ

## สิ่งที่ผมอยากให้จำ

**Webhook แบบ row-level จะคูณกับทุก bulk write เสมอ** ถ้า handler ของคุณมี early return อยู่บรรทัดแรก เงื่อนไขนั้นต้องไปอยู่ใน `WHEN` ของ trigger ด้วย ไม่งั้นคุณจ่ายค่า network เต็มราคาเพื่อโยนทิ้ง

**trigger ที่สร้างจากหน้า Dashboard ไม่ได้อยู่ใน migration** แปลว่าทุก environment ต้องตามไปแก้มือทีละตัว อย่าลืม

**`pg_cron` เดินตาม UTC และ `pg_net` เป็น fire-and-forget** job run details ขึ้นว่า succeeded แปลว่า "คิวสำเร็จ" ไม่ใช่ "ปลายทางตอบ 200" สถานะจริงอยู่อีกตารางนึงที่เก็บไว้ไม่กี่ชั่วโมงแล้วหาย ถ้าจะดูต้องรีบดู

**ตาราง log ของ webhook ไม่ถูกล้างเอง** ของเคสนี้โตไปถึง 6.47 ล้านแถว ต้องตั้ง retention เองครับ

และข้อสุดท้าย ซึ่งผมว่าสำคัญที่สุด — **ลองเอาอาการไปวางทับกับพฤติกรรมผู้ใช้ก่อนจะไปแตะสเปคเครื่อง** คำถามว่า "ทำไมต้องเช้า" พาไปหาคำตอบได้เร็วกว่าการอัปเกรด DB เยอะมากครับ
