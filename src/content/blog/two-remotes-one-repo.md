คืองี้ครับ มีอุบัติเหตุแบบหนึ่งที่ผมเชื่อว่าคนทำงานกับ CI/CD เจอกันแทบทุกคน คือ "เผลอ push แล้ว pipeline วิ่ง"

ไม่ใช่โค้ดผิดนะครับ โค้ดอาจจะดีมาก แต่มันยังไม่ถึงเวลาที่ควรขึ้น แล้วคำสั่งเดียวที่เราพิมพ์ด้วยความเคยมือ มันไปกดปุ่มที่เราไม่ได้ตั้งใจจะกด

วันก่อนผมไปเจอกฎการทำงานของโปรเจกต์หนึ่งที่จัดการเรื่องนี้ได้สวยมาก ด้วยไอเดียง่าย ๆ ที่เราทุกคนทำได้เลยวันนี้

## รีโป้เดียว แต่มีสองประตู

ปกติเราคิดว่า git repo หนึ่งตัวมี remote หนึ่งที่ ชื่อ `origin` จบ แต่จริง ๆ git ให้เรามี remote ได้หลายตัว ชี้ไปหลายเซิร์ฟเวอร์ก็ได้

โปรเจกต์นี้มีสองตัว สมมติเรียกว่าตัวหนึ่งอยู่บน GitHub อีกตัวอยู่บน GitLab

และนี่คือ แก่น ของเรื่องนี้ครับ — เขาไม่ได้มองสองตัวนี้เป็น "ที่สำรองของกันและกัน" เขามองว่ามันคน ละหน้าที่ กันเลย

- ตัวบน GitHub = ที่ทำงานประจำวัน push branch, เปิด PR, review โค้ดกันตรงนี้
- ตัวบน GitLab = ทางเดินของ deploy เท่านั้น

กฎคือ งานปกติ push ขึ้น GitHub อย่างเดียว ห้ามแตะ GitLab ยกเว้นตอนที่ "ตั้งใจจะ deploy" จริง ๆ

## ทำไมต้องแยก

ลองคิดภาพห้องครัวร้านอาหารครับ

เชฟซ้อมสูตรใหม่ ทำเสร็จก็วางไว้บนโต๊ะเตรียมอาหาร ชิมได้ แก้ได้ ทิ้งได้ ไม่มีใครเดือดร้อน

แต่ถ้าวางผิดโต๊ะ ไปวางบนเคาน์เตอร์ส่งอาหาร เด็กเสิร์ฟมาเห็นก็หยิบไปเสิร์ฟลูกค้าทันที เพราะหน้าที่ของโต๊ะนั้นคือ "ของพร้อมเสิร์ฟ"

remote ที่ต่อกับ CI/CD ก็คือเคาน์เตอร์ส่งอาหารครับ มันไม่ได้ถามว่าคุณพร้อมไหม มันมีหน้าที่หยิบไปทำต่อ

การแยกสองประตูเลยไม่ใช่เรื่องความเป๊ะหรือ OCD มันคือการทำให้ "การ deploy" กลายเป็นการกระทำที่ต้องตั้งใจ ไม่ใช่ผลข้างเคียงของการเซฟงาน

## deploy ก็ยังทำได้ แต่ต้องประกาศตัว

ของโปรเจกต์นี้ การ deploy ไม่ได้ใช้แค่ push เปล่า ๆ แต่ใช้ tag เป็นตัวสั่ง

เท่าที่บันทึกไว้คือมีสองรูปแบบ แบบหนึ่งเป็น hotfix ที่สั่ง build ใหม่ขึ้น UAT อีกแบบเป็นการ retag จาก image ของ DEV ที่ build ไว้แล้ว

จุดที่ผมชอบคือ การ deploy มันเลยต้อง "พิมพ์ชื่อ" ของสิ่งที่จะทำออกมาเป็น tag อย่างชัดเจน มันไม่ใช่การ push ที่เผลอได้ มันคือการเขียนเวอร์ชันลงไปตรง ๆ ว่าฉันจะส่งของนี้ขึ้นไป

เอาจริง ๆ นะครับ นี่คือหลักการเดียวกับที่เราทำกับอะไรที่อันตรายทุกอย่างในชีวิต — เพิ่มขั้นตอนให้มันช้าลงหนึ่งจังหวะ เพื่อให้สมองมีเวลาทัน

## สิ่งที่ผมเอากลับมาใช้

ไม่ต้องมีสอง remote ก็ใช้แนวคิดนี้ได้ครับ

ถาม ตัวเองสองข้อ หนึ่ง คำสั่งไหนในโปรเจกต์ผมที่ "ทำแล้วมีผลต่อคนอื่น" สอง คำสั่งนั้นมันแยกตัวเองออกจากคำสั่งที่ปลอดภัยชัดเจนพอหรือยัง

ถ้าสองอย่างนี้หน้าตาเหมือนกันเกินไป มันไม่ใช่เรื่องวินัยแล้วครับ มันคือดีไซน์ที่รอวันพลาด

อีกเรื่องที่ผมว่าสำคัญไม่แพ้กัน คือกฎแบบนี้เขาเขียนเก็บไว้เป็นเอกสารในโปรเจกต์ ไม่ได้อยู่ในหัวใครคนเดียว เพราะกฎที่ไม่ได้เขียนไว้ มันไม่มีอยู่จริงสำหรับคนที่เข้าทีมเดือนหน้าครับ
