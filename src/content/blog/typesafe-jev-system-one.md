เคยเจอไหมครับ เราเขียน prompt ยาวเหยียดบอก LLM ว่า "ตอบกลับมาเป็น JSON เท่านั้น ห้ามมีคำอธิบาย" แล้วมันก็ยังใจดีแถม "Sure! Here's the JSON:" มาให้ จน parser พังอยู่ดี

ผมว่าปัญหาจริงไม่ใช่ prompt ไม่เก่งพอครับ แต่คือเราเอาเครื่องมือผิดชิ้นมาใช้ตั้งแต่แรก

## เอาเครื่องคิดเลขไปเขียนเรียงความ

ลองคิดภาพร้านอาหารนะครับ งานในร้านมีสองแบบ แบบแรกคือเชฟคิดเมนูใหม่ ต้องครีเอทีฟ ต้องใช้เวลา แบบที่สองคือคนที่ยืนหน้าเคาน์เตอร์แล้วตัดสินใจว่า "ออเดอร์นี้เข้าครัวร้อนหรือครัวเย็น" — งานนี้ต้องเร็ว ต้องเหมือนเดิมทุกครั้ง และไม่ต้องบรรยายอะไรเลย

ที่ผ่านมาเราเอาเชฟมายืนหน้าเคาน์เตอร์ครับ แล้วก็แปลกใจว่าทำไมมันช้าและพูดมาก

TypeSafe AI เลยทำโมเดลชื่อ **Jev** ขึ้นมา เขาเรียกมันว่าโมเดลสาย **"System One"** — ชื่อยืมมาจากแนวคิด System 1 ของ Kahneman ที่หมายถึงการคิดแบบเร็ว ๆ ไม่ต้องเค้น

จุดที่ผมชอบที่สุดคือ Jev **ไม่ generate text เลย** ไม่ใช่ว่าไม่อยาก แต่มันทำไม่ได้ครับ มันออกแบบมาให้รับ "ข้อความ + ชุดคำถามที่ระบุ type ไว้" แล้วคืน "คำตอบตาม type นั้น พร้อมค่าความน่าจะเป็น" เท่านั้น

ซึ่งมันแปลว่าปัญหา JSON พังหายไปทั้งคลาส ไม่ใช่เพราะเราขอดีขึ้น แต่เพราะมันไม่มีช่องให้พูดเกินตั้งแต่ต้น

## ของจริงมีแค่สามชิ้น

Jev ให้คำถามมาแค่สามแบบครับ น้อยจนตอนแรกผมคิดว่าขาด แต่พอลองคิดตามก็พบว่าพอ

- **choice** — เลือกหนึ่งจากตัวเลือกที่ไม่มีลำดับ ใส่ได้ถึง 255 ตัวเลือก คืนมาเป็นตัวเลือก + probabilities + confidence
- **score** — ของที่มีลำดับ ตั้งได้ 2 ถึง 10 ระดับ คืนเป็นเลขทศนิยม คือมันตกกลางระหว่างระดับได้ด้วย
- **noul** — ใช่/ไม่ใช่ คืนค่า P(yes) ระหว่าง 0 ถึง 1 อันนี้ไม่มีช่อง confidence นะครับ

แล้วถ้าถามหลายคำถามในรีเควสต์เดียว ทุกคำถามเห็น state เดียวกัน และถูกประเมิน **แยกกันแบบขนาน** คำตอบข้อหนึ่งไม่เคยกลายเป็นบริบทของข้ออื่น

## ความมั่นใจที่เชื่อถือได้ (แบบมีเงื่อนไข)

Jev ถูกเทรนด้วยวิธีที่เรียกว่า RLCD เพื่อให้ค่าความน่าจะเป็น **calibrated** — แต่ตรงนี้ต้องอ่านตัวเล็กให้ดีครับ เอกสารเขาบอกว่า calibration ใช้ได้กับ "กลุ่มของการทำนาย" ไม่ใช่การันตีคำตอบเดี่ยว ๆ ทีละข้อ

วิธีใช้ที่เขาแนะนำคือมองมันเป็นแกนที่สองของการตัดสินใจ: มั่นใจสูง → ลงมือเลย, กลาง ๆ → ขึ้นธงให้คนยืนยัน, ต่ำ → ส่งต่อให้มนุษย์

และข้อนี้ผมคิดว่าสำคัญที่สุด — **เกณฑ์ความมั่นใจควรปรับตามความเสี่ยงของการกระทำ** การคืนเงินลูกค้ากับการแปะแท็กบทความ ไม่ควรใช้เลขเดียวกัน

เขายังแนะนำให้ยกคำถามและ threshold ทั้งหมดไปอยู่ในไฟล์ constants เดียว เพราะนั่นแหละคือสิ่งที่มนุษย์จะมารีวิว ฟังดูเป็นเรื่องเล็ก แต่เอาจริง ๆ นี่คือท่าเดียวที่ทำให้ระบบตรวจสอบได้

## ถามเยอะดีกว่าถามน้อย

อันนี้สวนความรู้สึกเดิมของผมเลยครับ

เอกสารเขาเรียกแพตเทิร์นนี้ว่า **speculative fan-out** คือยัดคำถามเยอะ ๆ ไปในรีเควสต์เดียว เพราะคำถามส่วนเพิ่มแทบไม่มีต้นทุน ใน cookbook เขายกตัวอย่างว่าจับ 13 คำถามรวมเป็นก้อนเดียว ได้ **ถูกลงราว 12 เท่า เร็วขึ้นราว 10 เท่า** โดยคำตอบเหมือนเดิม

จะยิงรีเควสต์ที่สองก็เมื่อ state หรือตัวเลือกรอบถัดไป *ขึ้นอยู่กับ* คำตอบรอบแรกจริง ๆ เท่านั้น

ด้านราคา ตอนที่ข้อมูลชุดนี้ถูกบันทึก (22 ก.ย. 2026) อยู่ที่ **$0.042 ต่อล้าน token ขา input และ output ฟรี** — แต่ย้ำว่านั่นคือเลขของวันนั้น เรื่องราคา ลิมิต และชื่อโมเดลมันขยับเร็ว อย่าไปอ้างต่อโดยไม่เช็คหน้า models ก่อนนะครับ

## ข้อจำกัดที่ต้องรู้ก่อนอิน

ผมไม่อยากให้อ่านจบแล้วคิดว่าเอาไปแทนทุกอย่างได้ มันมีกำแพงชัดเจนครับ

รับแค่ text — ไม่มีภาพ เสียง วิดีโอ ภาษาหลักคืออังกฤษ ภาษาอื่นรวมถึง CJK รับได้แต่ความแม่นลดลง ฉะนั้นถ้าจะเอามาทำงานไทย **ต้องทดสอบเองก่อน** อย่าเชื่อเพราะเดโมภาษาอังกฤษสวย

และมันไม่ใช่โมเดลสาย coding agent เอาไปแทนตัวที่ขับ Claude Code หรือ Cursor ไม่ได้ ท่าที่ถูกคือใช้ coding agent เขียนโค้ดที่ไป *เรียก* Jev

สรุปสิ่งที่ผมได้จากเรื่องนี้ไม่ใช่ "มีโมเดลใหม่มาแล้ว" ครับ แต่เป็นคำถามที่ควรถามตัวเองบ่อยกว่านี้ — งานที่เรากำลังจ้าง LLM ทำอยู่ มันเป็นงานที่ต้อง "คิด" หรือเป็นงานที่ต้อง "ตัดสินใจเร็วและเหมือนเดิมทุกครั้ง" กันแน่

ถ้าเป็นแบบหลัง เรากำลังจ่ายค่าเชฟเพื่อให้มายืนรับออเดอร์อยู่หรือเปล่า
